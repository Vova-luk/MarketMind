# Миграции общей базы MarketMind

SQL-файлы этой папки встраиваются в Go-бинарник через `embed` и применяются
пакетом `utils/migrator` с помощью Goose. API уже вызывает мигратор после
подключения к PostgreSQL и до запуска HTTP-сервера. При ошибке миграций API
не запускается. Tracking использует ту же схему `market_mind`.

Для запуска API с миграциями из `backend`:

```bash
cd services
go run ./api/cmd -config api/config/config.yaml -env-file ../.env
```

PostgreSQL должен быть доступен; настройки подключения берутся из конфига API.
Повторный запуск применяет только ещё не выполненные версии. История хранится
в таблице `public.goose_db_version`; параллельное применение защищено
PostgreSQL session lock.

## Схема

Миграции создают пять таблиц: `exchanges`, `markets`, `users`,
`subscriptions`, `alerts`. В `exchanges.id` используется `INTEGER` без
автогенерации: идентификаторы бирж задаются явно при добавлении справочника.
Миграция `002_create_exchanges.sql` сразу после создания таблицы добавляет
Binance (1), Bybit (2) и OKX (3), у всех `is_active = TRUE`.
Это начальное заполнение выполняется вместе с версией 002 при создании новой БД.
В БД, где версия 002 уже применена, изменение файла не добавит записи повторно.

Цены и значения алертов хранятся в `NUMERIC`, чтобы поддерживать дробные
значения без потери точности. Telegram ID пользователя, пара пользователь–рынок,
внешний инструмент на бирже и торговая пара на бирже защищены от дублирования. Внешние ключи сохраняют
заданный `ON DELETE CASCADE`; для запросов и удаления добавлены индексы.

### Торговые пары

`markets` хранит `external_id` в исходном формате биржи (`BTCUSDT`, `BTC-USDT`),
`base_asset` (`BTC`) и `quote_asset` (`USDT`, `EUR` и т. п.). Эти поля обязательны;
пустые значения, формат кодов и положительные цены проверяются приложением.
SQL `CHECK` не используются; `NOT NULL`, внешние ключи и `UNIQUE` сохраняются.
API получает их из метаданных Exchange-Data, а не делит внешний ID по разделителю.
Цена — количество `quote_asset` за одну единицу `base_asset`.
`created_at` и `updated_at` задаются при создании рынка. PostgreSQL обновляет
`updated_at` при записи `price`. Карточка подписки возвращает это время в UTC.

Уникальны `(exchange_id, external_id)` и `(exchange_id, base_asset, quote_asset)`.
BTC/USDT и BTC/EUR — разные рынки на одной бирже; один и тот же
внешний ID разрешён на разных биржах. Модель предназначена для spot-инструментов.
Отдельной таблицы монет нет: базовый актив и валюта котировки хранятся прямо в рынке.
В поиске API формирует `display_name` из двух кодов актива. Для подписок фронт
собирает подпись из `base_asset` и `quote_asset`.
В алертах `reference_price` и абсолютная цель имеют валюту котировки рынка подписки;
дублировать код валюты в таблице `alerts` не требуется.

### Список для Exchange-Data

Планируемая служебная ручка `GET /internal/v1/tracked-markets` возвращает рынки
всех пользователей, сгруппированные по активным биржам. Один рынок возвращается
один раз, независимо от числа подписок и наличия активных алертов:

```sql
SELECT m.id AS market_id, m.exchange_id, m.external_id
FROM market_mind.markets AS m
JOIN market_mind.exchanges AS e ON e.id = m.exchange_id
WHERE e.is_active
  AND EXISTS (
      SELECT 1 FROM market_mind.subscriptions AS s WHERE s.market_id = m.id
  )
ORDER BY m.exchange_id, m.id;
```

Exchange-Data читает этот список из API, получает цены у бирж и публикует
изменённые цены в Kafka (`Price-Checked-Topic`). Tracking читает события и
проверяет алерты. HTTP-ручка не принимает обновления цен.

По запросу владельца проекта изменение внесено в исходные миграции `001`, `003` и `006`,
новой версии нет. Оно применяется при создании новой БД. Goose не переисполняет
уже применённые версии: существующая БД сама от этой правки не обновится.
Сохраняемую БД нужно отдельно мигрировать с заполнением метаданных из Exchange-Data;
чистую тестовую БД можно создать заново. Эта правка не удаляет и не обновляет
данные запущенных БД.

## Добавление миграции

Одна версия — один файл, например `007_add_alert_state.sql`:

```sql
-- +goose Up
-- Изменение схемы.

-- +goose Down
-- Обратное изменение.
```

В обычном процессе уже применённые версии не редактируются: изменения добавляются
следующим файлом. Исключение для текущей правки исходной схемы описано выше.
Goose использует транзакции по умолчанию. Полный откат удаляет таблицы в обратном
порядке, а затем схему `market_mind`, без `CASCADE` при удалении схемы.

## Проверка и ручной откат

Для ручного управления можно установить CLI той же версии, что в `go.mod`:

```bash
go install github.com/pressly/goose/v3/cmd/goose@v3.29.0
```

Из `backend/services`, указав строку подключения в `GOOSE_DBSTRING`:

```bash
export GOOSE_DRIVER=postgres
export GOOSE_MIGRATION_DIR=utils/migrations
goose status
goose up
goose down
```

`down` откатывает одну последнюю миграцию. Откат удаляющих таблицы версий
удаляет и их данные; полный цикл проверки выполняется на отдельной тестовой БД.

## Автоматические тесты

```bash
go test ./utils/migrator
```

Без `MIGRATOR_TEST_DSN` выполняются проверки упаковки миграций, уникальности
версий и обработки ошибок. Для полного PostgreSQL-теста задаётся
`MIGRATOR_TEST_DSN` — строка подключения с правом создавать базы:

```bash
go test -race -count=1 -run TestMigrationLifecycle -v ./utils/migrator
```

Тест создаёт собственную БД `marketmind_migrations_*` и удаляет только её.
Он проверяет первый и повторный `Up`, несколько валют котировки одной монеты,
исходный формат ID биржи, ограничения и точность чисел, одиночный
`Down`, полный откат, повторное применение и атомарный откат ошибочной миграции.
В CI PostgreSQL запускается отдельным сервисом, поэтому этот тест не пропускается.
